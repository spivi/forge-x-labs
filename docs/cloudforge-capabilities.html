Overview

The value is the labeled, validated risk graph — not the Terraform

Most tools that "generate misconfigured infrastructure" hand you HCL and stop. cloudforge inverts that: the source of truth is a normalized risk graph with attached ground truth (the exact critical paths, the expected scanner findings, the remediation order). The Terraform is a compiled artifact emitted from that graph purely so a static scanner has something to read — it is never applied.

That gives you something you can score against: run a scanner over the generated Terraform, then measure what it detected against the graph's known-answer findings. cloudforge is two tools sharing one discipline:

The two halves: a scenario engine (generate → validate → report) that emits benchmarkable scenarios, and a learning corpus pipeline (cloudforge learn …) that ingests provenance-controlled risk patterns into a training-ready dataset. Both are fully local and deterministic.

The contract

What it does, and what it will not do

The second column is a hard boundary, enforced in code — read it before you test. cloudforge is a defensive research tool; its guarantees are as much about restraint as capability.

Capabilities

  • Generates labeled risk graphs with ground-truth critical paths + expected findings
  • Emits valid-for-static-analysis Terraform that maps 1:1 back to graph nodes
  • Runs a benchmark score: expected findings vs. what a scanner actually detected
  • Produces seeded, risk-preserving mutations for dataset diversity
  • Builds a provenance-stamped corpus and a gated training export
  • Degrades fail-soft when optional scanners are absent

Hard boundaries

  • Never runs terraform apply — a validator rejects any deployable: true scenario
  • Needs no cloud account and no credentials; account IDs are dummy (000000000000)
  • No offensive / exploit / operational-attack content — a keyword scan quarantines it
  • No ML, LLM, diffusion, or GPU — generation and scoring are pure deterministic rules
  • Fetches internet content only from an allow-list registry — no crawling, no scraping, an honest User-Agent, a 10 MiB response cap
  • No provenance, no corpus; restricted-license & unsafe content are excluded from export

Half one · scenario engine

generate → validate → report

Three commands are the whole pipeline. generate compiles a scenario spec into a full artifact tree; validate runs the check suite (fail-soft on missing tools); report renders a human-readable report.md.

cloudforge generate <scenario.yaml> --out DIR [--mutate-seed N]

Compile a scenario spec into the artifact tree. --mutate-seed emits a seeded, ground-truth-preserving variant (same seed → byte-identical graph).

cloudforge validate <scenario-dir>

Run schema, graph-risk, Terraform, scanner, and OPA checks. Exits non-zero only on a real FAIL; a missing optional tool is a WARN.

cloudforge report <scenario-dir>

Render report.md: the risk narrative, critical path, findings, scanner score, and remediation order. Loads artifacts from disk — works standalone.

Half two · learning corpus

cloudforge learn — a provenance-controlled risk-pattern pipeline

The learn command group turns cloud-risk patterns into a training-ready dataset without ever touching a model. Every record carries full provenance; the export gate is a licensing and safety boundary, not just a quality filter.

learn fetch-sources

Fetch every enabled registry source into data/raw/. The only command that touches the network — and only for allow-listed sources.

learn ingest --adapter NAME --corpus FILE

Run one adapter over its cached source, normalizing records into the corpus JSONL.

learn validate-corpus --corpus FILE

Fragment + corpus-level checks; prints PASS/FAIL, exits 1 on FAIL.

learn summarize --corpus FILE

Coverage by provider / domain / weakness family, plus the quality-score distribution.

learn export-training --corpus FILE --out DIR [--include-restricted]

Apply the export gate; write the JSONL bundle + a coverage manifest.

The source registry — an allow-list, governed by reuse status

Nothing is fetched or ingested unless it is listed in data/source_registry.yaml and enabled. Each source's reuse_status decides how far its content may travel into a training export.

Adapters & the seed catalog

Three adapters translate a raw source into normalized RiskPattern records: rule_catalog_yaml (the local hand-authored seed catalog), checkov_policy_index (metadata-only), and cloudforge_scenario (ingest your own generated scenarios). The shipped seed catalog holds 14 hand-authored patterns across AWS, Azure, and GCP — each a semantically-correct risk graph fragment with real node types and edges, not a heuristic guess.

The honest export number: feeding the 14-pattern seed catalog through the gate yields 12/14 exportable. The two excluded are missing-logging patterns whose risk is an absent edge — structurally simple, so they legitimately fall below the 0.70 quality bar. The manifest records exactly why each was excluded. Nothing is inflated to hit a number.

The discipline

Validation is fail-soft, and every check is real

Optional external tools (terraform, checkov, opa) are probed at runtime. If present, they run for real; if absent, that check is a WARN and never changes the exit code. Here is validate on a machine that has all three installed — note the benchmark score and the graph-connectivity check:

cloudforge validate · ci_cd_iam_chain
cloudforge validate out/scenario_001
[PASS] scenario schema valid.
[PASS] graph schema valid.
[PASS] terraform validate.
[PASS] checkov scan. results written to scanner_results/
[PASS] scanner score. 4/5 expected findings detected (coverage 0.8)
[PASS] opa policy.
[PASS] ground-truth nodes exist.
[PASS] ground-truth edges exist.
[PASS] ground-truth path exists.
[PASS] critical-sink connectivity.
[PASS] scenario constraints satisfied.
[PASS] no forbidden permissions.
[PASS] broad grants documented by findings.

The graph-risk engine is stdlib-only (BFS reachability, no dependencies). Two of these checks are the parts most worth probing: no forbidden permissions rejects any node granting a destructive action (iam:Delete*, s3:DeleteBucket, ec2:TerminateInstances, kms:ScheduleKeyDeletion, organizations:*), and critical-sink connectivity requires the critical-risk edge and the sensitive-data sink to lie on one reachable path — a disconnected graph is rejected even if both pieces exist.

The stress epic · FXL-STRESS-1

Attacked on purpose — 7 integrity bugs found and fixed

A "no bug" result on a security tool is only worth anything if someone tried hard to break it. So a full epic did exactly that: 15 adversarial clauses (S1–S15), each one a written guarantee, each attacked from an independent angle — property-based, differential, corpus-fuzzing, scanner-scoring, OPA policy, and CLI failure-mode. Every guarantee now has a test that exists specifically to make it fail. The suite grew from 889 to 1,746 tests.

Adversarial angles

What to poke at

The interesting question for a tester is not "does it generate a scenario" — it's "can I make it lie, apply, leak, or crash?" Concrete things to try:

AttackExpected behavior
Set deployable: true in a scenario specRejected at load — the deployable field validator forbids it. The tool structurally cannot produce an appliable scenario.
Hand-edit graph.json to grant iam:Delete* and re-validate[FAIL] forbidden permission…, non-zero exit. The risk engine scans node action lists against the forbidden set.
Feed hostile graph field values (HCL injection: ${…}, %{…}, quotes, path traversal, unicode)Either safely escaped in the emitted HCL or rejected with a clear validation error. Covered by a dedicated adversarial corpus under tests/security/ — including 108 hostile values driven through real terraform.
Build a graph where the critical edge and the sensitive-data sink are on disconnected components[FAIL] critical-sink connectivity — existence is not enough; they must share a reachable path.
Put exploit / persistence / credential-theft wording in a source patternClassified unsafe_operational by the keyword scan and excluded from the training export — even with --include-restricted.
Try to export a restricted or metadata_only source into training dataExcluded by the gate. --include-restricted relaxes only restricted-license sources, never unsafe content, and the manifest records that the flag was used.
Collide two node ids that sanitize to the same Terraform labelRejected pre-emission with a GraphIntegrityError naming both nodes — no duplicate-resource Terraform error.
Reproducibility is part of the contract. Same input → byte-identical output. Same --mutate-seed → byte-identical variant. The corpus normalizer, dedup, and quality scoring are all deterministic — no randomness, no model calls — so any non-determinism you find is a bug worth reporting.

Current frontier · FXL-VAR-1

What's shipped vs. what's in flight

An honest note, because the boundary matters. Investigation confirmed what the code already admitted in its own docstrings: today's generators produce cosmetic variation only. TemplateGenerator returns a fixed literal graph per family; the mutation engine changes names, tags, and one spare subnet — node ids and every ground-truth edge are deliberately left untouched. That is why same-seed output is byte-identical, and it is exactly the property the stress epic verified. It also means the two shipped families give roughly one graph-shape per family.

The variation-validation epic closes that gap: assemble scenarios from typed fragments — each owning its own node ids, edges, findings, and ground-truth entries — so real topology and risk-shape variation becomes possible without artifacts ever disagreeing by construction. A companion harness measures graph-shape diversity at scale, and its diversity thresholds are the acceptance test for the depth work, so subject and measurement can't drift apart. Every stress-hardened safety invariant is preserved as a hard backstop.

Rationale

The decisions that shape the boundaries

These are recorded design decisions; they explain why the guarantees above hold.

  • FXL-D002Deterministic, rule-based generation first — validators and ground truth matter more than generation cleverness.
  • FXL-D003A scenario is "validated" only against a 12-point, benchmark-grade definition.
  • FXL-D004Harden validation before adding generator depth — the integrity layer must be attack-proof before scenarios get more varied.
  • FXL-D006Node ids that sanitize to the same Terraform label are rejected pre-emission, scoped per resource type.
  • FXL-D007CSA CCM control-ID mappings are training-eligible; the control text is not; CIS stays restricted.
  • FXL-D008OPA stays a coarse, family-agnostic gate; the graph engine owns precise path reachability (defense in depth).
