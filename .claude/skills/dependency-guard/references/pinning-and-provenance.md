# Pinning, Hashing & Provenance

How to pin "as best practice gives" for each manager, why hashes matter, and how
to read provenance. Plus the hook snippet for deterministic triggering.

## Why this matters

A floating constraint (`^1.2`, `>=1.0`, `latest`) means the artifact you tested
is not necessarily the artifact that gets installed next week — that gap is both
the supply-chain window (a compromised release lands silently) and the breakage
window (a minor bump changes behavior). Pinning closes the gap; hashing proves
the bytes you pinned are the bytes you got.

## Application vs library

The right pin depends on what the project *is*:

- **Application** — a deployed service, CLI, or anything not consumed as a
  dependency by someone else. You control the whole environment, so pin as
  tightly as possible and reproduce exactly. **This is the default and the
  fallback when unsure.**
- **Library** — published to a registry for others to depend on. Over-pinning
  here forces your constraints onto every consumer and causes resolver
  conflicts, so declare a **compatible range** in the manifest — but still keep
  a committed lockfile with hashes for your own dev/CI reproducibility.

Detect "library" by: a `[build-system]` / publish config, a `packages`/`name`
meant for distribution, or an existing registry presence. Otherwise treat as an
application.

## Per-manager mechanics

### Python — Poetry
- Manifest constraint: app → `package = "1.2.3"` (exact) or a narrow
  `">=1.2.3,<1.3"`; library → `"^1.2"` is acceptable.
- `poetry.lock` already hash-pins the **entire transitive tree** — this is the
  real guarantee. Ensure it is **committed**.
- Verify resolution before trusting: `poetry add <pkg>@<ver>` updates the lock;
  confirm the new entry has a `[[package]]` block with `files = [{hash=...}]`.
- Blast radius preview: `poetry add <pkg> --dry-run`.

### Python — pip / requirements
- App best practice is a **hash-pinned** `requirements.txt` generated by
  `pip-compile --generate-hashes` (pip-tools) or `uv pip compile --generate-hashes`.
- Install with `pip install --require-hashes -r requirements.txt` so an
  unhashed/tampered artifact is rejected.
- A bare `pip install <pkg>` with no version and no hash is the weakest case —
  always resolve to an exact version and record it.

### Python — uv / pdm
- `uv add <pkg>==<ver>` → `uv.lock` (hashed). `pdm add` → `pdm.lock` (hashed).
- Commit the lockfile; both support `--frozen`/locked CI installs.

### Node — npm / pnpm / yarn
- `npm install <pkg>@<ver> --save-exact` writes an exact version (no `^`).
- The real guarantee is the committed `package-lock.json` / `pnpm-lock.yaml` /
  `yarn.lock`, which records `integrity` (subresource-integrity hash) per package.
- CI installs from the lock only: `npm ci` (never `npm install` in CI).
- Provenance: `npm audit signatures` verifies registry signatures + provenance
  attestations; prefer packages published with `--provenance` (sigstore).

### Rust — cargo
- `Cargo.toml` with `=1.2.3` for exact; `Cargo.lock` (committed for apps) pins
  the resolved set with checksums from the registry index.

### Go modules
- `go get <module>@<version>` pins in `go.mod`; `go.sum` records cryptographic
  checksums. Never delete `go.sum`. `GOFLAGS=-mod=readonly` in CI.

### Ruby / PHP / .NET
- `Gemfile.lock`, `composer.lock`, and `packages.lock.json`
  (`<RestorePackagesWithLockFile>`) are the hashed lockfiles — commit them and
  install in locked/frozen mode in CI.

## Reading provenance

- **PyPI (PEP 740)** — newer releases may carry digital attestations from
  trusted publishing (GitHub Actions + sigstore). Present = stronger origin
  guarantee. Absent ≠ malicious, but it's a soft signal, especially on a young
  or low-traffic package.
- **npm provenance** — `dist.attestations` on a version + a green
  `npm audit signatures`. Packages built in CI with `--provenance` link the
  artifact to the source commit and builder.
- **sdist vs wheel (Python)** — an sdist runs `setup.py` at install time
  (arbitrary code execution on the installing machine). Prefer wheels; an
  sdist-only release is a soft flag worth noting.

## Hook (deterministic triggering)

Description-based skill triggering under-fires on dependency adds — they look
like trivial one-step tasks, so the model often just runs the install without
consulting the skill (measured recall ~22%). The hook is therefore the
*primary* enforcement, not a backstop. The logic lives in
`scripts/depguard_hook.sh` (pure bash + grep, reads the hook JSON on stdin —
**not** any env var; degrades gracefully without `jq`). Two matchers point at
it, already wired in this project's `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "timeout": 10,
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/skills/dependency-guard/scripts/depguard_hook.sh" }] },
      { "matcher": "Edit|Write|MultiEdit",
        "hooks": [{ "type": "command", "timeout": 10,
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/skills/dependency-guard/scripts/depguard_hook.sh" }] }
    ]
  }
}
```

What the script does:
- **Bash matcher** — emits an `ask` permission decision when the command adds a
  dependency or expands a package source (`poetry add`, `npm i <pkg>`,
  `cargo add`, `brew tap`/`brew install`, `apt install`, `go get`, …). Stays
  silent for lockfile reinstalls (`poetry install`, `npm ci`, `pip install -r`,
  `bundle install`, …) — no new trust decision there.
- **Edit|Write|MultiEdit matcher** — emits `ask` when a dependency *manifest*
  (`pyproject.toml`, `package.json`, `Cargo.toml`, `requirements*.txt`,
  `go.mod`, `Gemfile`, `composer.json`, `pom.xml`, `build.gradle`, `*.csproj`)
  is edited with text that carries a version specifier. This closes the path
  where a dep is added by editing the manifest directly instead of via a CLI.

Notes:
- `ask` surfaces a permission prompt with a reason (it does not hard-block, so
  there's no install/deny loop). The skill is the real vet → pin → verify gate.
- A newly *added* hook event (e.g. first `PreToolUse`) is not hot-loaded into a
  running session — open `/hooks` once or restart to activate it that session.
- Known minor over-trigger: editing a manifest's own `version = "x.y.z"` line
  can prompt, since it matches a version specifier. Just approve — cheap.
- Tune the `add` / `manifest` patterns in the script to your toolchain.
